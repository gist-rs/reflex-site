FAQ

What are the lanes?

Reflex · modelless — no neural weights: decisions come from a per-label corpus plus a fitted sigmoid gate, so it answers in micro-seconds and is bit-deterministic on a given build. laya (rust) — our Rust port running the open-weights laya checkpoints on the local GPU (device noted per run: Metal, or the Apple Neural Engine where the lane serves it). laya (python) — the original torch reference, driven as a subprocess oracle on the same cases. clm — the external Contrastive-LM reference (Apache-2.0, not affiliated): Qwen3-8B pooling + trained heads, served on its own stack and measured on ours — a comparison lane (full detail in the clm entry below). gliner — the external GLiNER2.5-Decide zero-shot classifier (Apache-2.0, not affiliated, 340M DeBERTa-v3 encoder): their gliner2 package answers the same candidate-label questions — a comparison lane, never a product lane. agentjev — the external AgentJev-0.6B typed-decision specialist (Apache-2.0, not affiliated, Qwen3-0.6B backbone): their service answers over HTTP, measured gold-label on our split — a comparison lane, never a product lane. Instinct — the trained-specialist hybrid (riir-instinct): a BLAKE3-sealed distilled specialist composed with Reflex — the modelless lane's fused gate decides when to consult it; the cell is the registered arm's single frozen test read over the same seat and protocol as every other lane (per suite, only where a hybrid arm won pre-registration). openthai — the external OpenThai-SystemOne decision specialist (Apache-2.0, not affiliated, Qwen3.5-0.8B backbone): their FastAPI service answers the same decision questions, measured gold-label on our splits — a comparison lane, and the board's Thai-capability row.

Tell me more about the clm lane

CLM (Contrastive Language Models) is an external, unaffiliated research project — an Apache-2.0 "System One" decision model (Kwok, Kang, Suresh, Saad-Falcon, Pavone, Ré, Mirhoseini — github.com/Contrastive-LM/CLM · project blog). Architecture: a frozen Qwen3-8B encoder with last-token pooling plus ~20M-parameter state/action heads trained with a contrastive (InfoNCE) objective, so a softmax over state–action scores is the answer distribution. These rows use their reference head CLM-v0.1-8B (75 MB, on Hugging Face).

How we measure it: their stack serves, ours measures. The lane runs on the 4090 box — one vLLM Qwen3-8B pooling server plus clm-serve (the heads) behind their TypeSafe-compatible /v1/systemone endpoint — and our harness drives it with the same byte-identical questions as every other lane. Their prompt/prose rendering is byte-pinned against the reference implementation (goldens generated from their own Python at the pinned commit cca045ff), so the comparison is their rendering law, not our paraphrase of it. Latency figures include the HTTP round-trip, and their published "9× vs Jev" speedup — measured against Jev's remote endpoint, network included — deliberately does not carry into these tables. CLM is a comparison lane only: it is not part of Reflex and ships in no release; accuracy columns compare it exactly as they compare everyone else.

What is the ANE device row?

Some laya (rust) runs serve from the Apple Neural Engine — the encoder executes as one compiled whole-graph Core ML model per length bucket (BC1S, FP16), while the gather and the decision head stay host-side. FP16 math fails a bit-level drift bar by nature, so the ANE rows are gated the way every device row should be: decision-level — top-1 agreement against the frozen reference captures (gate ≥ 99.9%), and every argmax flip must sit inside the near-tie band (the reference's own top-2 margin < 0.04). Every flip, near-tie or not, is listed — never hidden. Probability drift is published as observation, never as a gate. Sequences longer than the largest bucket are served by the other devices and named as skips on the ANE row.

Why does the modelless lane lose on accuracy?

It is corpus-bound by design: out-of-domain text lands near chance, and those rows are published rather than trimmed. Its axes are latency and selective accuracy — how right it is on the questions it chooses to answer (acc@50cov, abstain / sel-acc) — not raw accuracy against a neural model.

Where the gap was the scorer rather than the domain, it closes. Per-label count tables (naive-Bayes log-odds over the train rows, plus a sentence-pair view for premise/hypothesis tasks) are cal-selected per suite, and the test split is read once. That took several suites to or past the laya lanes at the same sub-millisecond latency (riir-reflex Bench 051). The test split never enters a corpus. A separate transductive line under each table shows what happens if the engine may also read the test text (self-labelled, gold never read): it adds nothing, because the train rows already carry the vocabulary.

Why are the rust and python bars the same length on accuracy?

They should be: the rust lane is a port of the same checkpoints and is checked against the python oracle's own outputs per suite. What differs is latency — and the python figure includes the subprocess round-trip (IPC).

Why is latency on a log scale?

The lanes are orders of magnitude apart. On a linear axis every modelless bar would be invisible; on the log axis each gridline is 10×, so bar length compares ratios, not differences. When a lane lands far past the readable range the axis breaks — the same slanted break sign the sizes chart uses: the log axis runs to 500 ms over most of the track, and a bar past the sign continues on a compressed scale, its exact value on the cell and in the tooltip.

What do acc@50cov and abstain / sel-acc mean?

acc@50cov is accuracy on the half of the questions the lane is most confident about. abstain / sel-acc is the fraction the calibrated gate declined to answer, and the accuracy on the rest.

What does G1 PASS / FAIL / NO CLAIM mean?

G1 gates calibration honesty only: does the fitted confidence beat both the raw readout and the conformal-naive floor? It is not an accuracy gate. FAIL means the calibrator had nothing to improve; NO CLAIM means it never fitted (the calibration window was too thin) — neither means the answers got worse.

Why is a bar missing?

That lane did not run on that suite (for example, a suite that only the LLM lane can answer). A missing bar reads "not run", never zero.

Are these numbers hand-typed?

No. Charts and tables are both drawn in your browser from data/bench.json, which is generated from the harness output. Re-publishing that file re-draws everything.

Notes

How to read these numbers
  • Every lane sees byte-identical questions. No single "we win" number exists or will exist.
  • The modelless lane's near-chance rows on out-of-domain text are structural — it is corpus-bound by design — and are published rather than trimmed.
  • G1 gates calibration honesty only (does the fitted confidence beat the raw readout AND the conformal-naive floor?). A FAIL means the calibrator had nothing to improve, never that answers got worse.
  • Every row names its machine with an @host tag (chip + device): @m3-max-metal is this page's baseline machine serving the laya lane from Metal, @4090-win is a different box, and @m3-max-ane is the same M3 serving the laya lane from the Apple Neural Engine — a device row (laya lanes only; the modelless lane uses no neural device and always reads from the @m3-max-metal row). Hardware for every box: Machines below.
  • † on a latency cell: the run that measured that timing judged its own machine unfit to quote latency (load or power, riir-reflex's box check) — shown so nothing is hidden, not quotable. A cell with no mark was either fit, unjudged (a host with no box probes; hover for which), or published before the check was recorded.
  • Accuracy chance level differs per suite (a 3-way and a 77-way task are not comparable) — compare lanes within a suite, never one suite's bar with another's.
  • The hero chart shows one checkpoint per laya lane: the best non-multilingual one for that suite, picked once by accuracy so every metric toggle shows the same run. Every checkpoint (multilingual included) is in the per-suite tables.
  • p99 on a small suite is effectively its maximum (under ~100 samples the 99th percentile lands on the last one) — read p99 on the harness_* suites as "worst observed", not a tail estimate.
  • Bit-identity across runs is claimed for the modelless lane only; the laya lanes get the same repeat check, reported under det, not claimed.
  • Latency is wall-clock on the host named in the provenance line above; it moves with the machine and its power state. Modelless accuracy does not — the publisher refuses to merge a host whose modelless accuracy drifts.
  • Why the openthai massive_intent_en row is ~1.7 s on @m3-max-metal but 95 ms on @4090-win: the openthai model reads every option as prompt text — the input template inlines each option (<|ts_opt_i|> option: description) and one forward scores all 256 slots at the answer position, so per-question cost scales with option count. massive carries 59 options (~203 tokens/question) vs xnli's 3, and on MPS fp32 that prices at ~29 ms per option (~1.7 s/question). The 4090 prices the identical prompts at 95 ms — same design, same accuracy (0.9200 byte-identical across both hosts), ~18× cheaper tokens. Verified as real, not box contamination: a preflight-passed exclusive-GPU re-read reproduced the number within 5% and made every @m3-max-metal openthai cell quotable from its own run (reflex Bench 085).
