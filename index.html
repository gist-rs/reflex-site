How it works

One pipeline, no trained weights: embed the state, route to the matching corpus, score every option corpus-is-the-model, calibrate with a sigmoid gate — then answer, or abstain. The thresholds come from your labeled data, fitted offline. The full write-up: .docs/03_decision_flow/decision_flow.md.

Coming from LLMs? The two lanes, mapped.

Reflex's decision core is modelless — if your instinct is new domain → collect data → fine-tune, the loop you know isn't here. The corpus is the model, and the fitting that does exist is a build step, not a training run. Here is what each lane actually is: the product lane (KatGPT modelless) and the open-weights lane it is measured against (laya). Accuracy and latency live on the benchmark page; this is about the machinery.

KATGPT MODELLESS — the product lane

The corpus is the model.

  1. Fit time: a build step, not a training run. You author documents per domain. The build derives three artifacts from them — an LZ4 drafter over the text (a compression model of the domain), a unit centroid (the domain's routing direction), and a distance gate (what "in-corpus" means) — and can optionally fit per-label linear heads from the same labeled docs.
  2. Serve time. Embed the state — hashed bytes through a fixed projection — route by cosine to the closest domain, score every option by the bytes it adds to the context's compressed form blended with its cosine to that option's corpus (plus an optional fitted-head term), normalize with a sigmoid, then pass two thresholds fitted offline from your labeled slice. Answer — or abstain.
  3. New domain. Write documents, label a small calibration slice, refit. No GPU, no dataset pipeline. The "checkpoint" is a folder of text you can read and diff in a PR — and a refit is bit-identical.
LAYA — the open-weights comparison lane

The weights are the model.

  1. Fit time: someone else's training run. Pretrained 322M–421M encoder checkpoints arrive with weights fixed. The typed lane is a separate specialist checkpoint, trained on the typed-decision distribution.
  2. Serve time. Tokenize, run one forward pass, read per-option probabilities off the head.
  3. New domain. Accept the base checkpoint's zero-shot behavior — or produce a new specialist: a dataset and a training run.
  4. Role here. A comparison, never a dependency. The lane rides the binary but its weights do not ride the archive — they load from Hugging Face at runtime (SHA-256-verified) and are never redistributed.

So where does the learning happen?

In small, deterministic, replayable fits — not a training run. The confidence calibration is a 2-parameter Platt-style solve (Newton, bit-identical on replay); the two abstain thresholds are percentiles of your calibration slice; and, where a lane opts in, per-label linear heads are fitted at build time by a short fixed-order SGD that also replays bit-identically. No neural network is trained, no GPU is booked. Optionally, the running engine keeps learning its calibration: a /feedback endpoint refits it from outcome observations.

Is this RAG? k-NN?

Closest cousins: nearest-centroid classification for routing, retrieval-flavored scoring for options. The twist is the scorer — an LZ4 drafter treats the corpus as a compression dictionary, so "how many bytes does this option add to the context" is a predictability signal with no learned parameters. The cosine term is what actually ranks options; the drafter delta alone can't (a 4-byte option barely moves a ~300-byte context's compressed size).

When does each lane make sense?

The modelless lane is native territory when the answer space is typed and the domain is yours to describe: routing states, code spans, workflow decisions — anywhere you can author documents and label a calibration slice. Trained checkpoints win where you can't author the domain: broad pretraining knowledge, open-class NLU. They also compose — the abstain is a routing decision for the caller, so a declined local answer can escalate to a model only when there's signal to gain.

And the game boards — where does the "grammar" live?

The arena's game heads encode state and options as closed-grammar sentences, so every answer decodes back to exact feature values. That grammar is a lane-local convention for game boards — not the engine's. For text domains, the documents themselves are the vocabulary: no grammar authoring, just docs.

Which agents does it work with?

Claude Code reads .claude/skills/ natively; Zed reads .agents/skills/. And any agent that accepts a markdown instruction file works — the skill is plain instructions plus exact HTTP calls your agent already knows how to make.

What does it change?

Without it, an agent asked to classify, route, or triage reaches for an LLM call. With it, it starts a microsecond-tier local engine, asks typed questions with the answer space defined at request time, fits confidence thresholds from your labeled data, wires abstention into a fallback path instead of an error — and reports measured accuracy instead of a guess.
